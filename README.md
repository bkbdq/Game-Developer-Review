# Game-Developer-Review

> 一个面向游戏行业从业者的匿名公司评价平台：说真话，不被认出来。

- 展示站：https://goodcorp.games/
- 匿名问卷：https://survey.goodcorp.games/
- GitHub Pages 镜像：https://github.goodcorp.games/
- 开发预览：https://dev.goodcorp.games/

## 这是什么

Game-Developer-Review 是一个游戏行业的匿名评价平台。你可以匿名写下自己待过的游戏公司、参与过的项目、真实的加班与福利情况、管理方式和项目体验，帮助后来者在下一次求职或合作前，看到招聘 JD 之外的另一面。

平台不做社交，不做热搜，也不追求“爆料”。我们只记录一件事：**在这家公司、这个项目里工作，真实感受是什么。**

所有提交都会经过人工审核。审核通过后，评价会以匿名形式进入公开数据，并在展示站上按公司和项目聚合展示；审核不通过的内容不会公开，也不会出现在任何搜索结果里。

## 解决什么问题

游戏行业的招聘信息高度不对称：

- 招聘 JD 写的是“扁平管理、弹性工作”，实际可能是长期 10 点后下班
- 项目是否被砍、是否频繁换方向、是否有年终，外部很难提前知道
- 在职的人不敢说，离职的人说了也容易被当成“前员工情绪”
- 零散信息散落在匿名社区、群聊和面试口头相传里，无法比较，也无法沉淀

我们想提供一个更稳定的参考系：**结构化的匿名评价 + 人工审核 + 公开可查的数据**。它不替任何人做决定，但可以让决定之前多一点事实。

## 你能看到什么

- 公司目录可按评价等级、评价数量和最近更新排序，可用公司名或别名搜索。
- 公司和项目都在满 5 篇评价后显示等级。好评率取四、五星评价在好评和差评中的比例。三星计入中评和总篇数。
- 项目发现展示精选评价、项目状态和可翻组的近期好评项目。入选项目平均分至少 4.0 / 5、累计好评率至少 70%，且近 30 天有好评，按该时段的好评篇数排序。
- 公司和项目主页可以直接进入已预填的问卷。

公司少于 5 篇评价时，公司页评价卡隐藏项目与在职时长。项目少于 5 篇时，项目页评价卡隐藏在职时长。评价日期显示到月份。

## 我们坚持什么

**匿名优先。** 不收集姓名、邮箱、手机号或账号；IP 只以加盐哈希形式短期保存，用于防刷和去重，不用于识别个人。

**人工审核。** 每条内容都会由管理员检查：脱敏、去掉广告和联系方式、处理人身攻击和未公开的商业秘密。审核不通过的内容不会进入公开数据。

**公开数据。** 审核通过的评价以 JSON 文件形式存放在公开仓库，任何人可以查看、下载和比对历史。数据格式有 schema 约束，变更可追溯。

**审核后更新。** 展示站不是实时社区，只有审核通过的内容才会触发一次静态更新。慢一点，但更干净。

## 怎么运作

```text
匿名问卷（survey.goodcorp.games）
        │ 提交，写入 D1 待审队列
        ▼
管理员控制台（本地 127.0.0.1 或 admin.goodcorp.games）
        │ 审核、脱敏、通过或拒绝
        ▼
公开数据仓库（GitHub main）
        │ 审核通过后写入 data/
        ├──────────────────────────────┐
        ▼                              ▼
本地控制台构建正式站             GitHub Actions 构建
（只读 data/）                   （只读 data/）
        ▼                              ▼
Cloudflare Pages gdr-site       GitHub Pages 镜像
goodcorp.games                  github.goodcorp.games
```

审核通过后，本地控制台会自动从 `main` 拉取最新数据、构建正式站并部署到 Cloudflare；GitHub Actions 同时把同一份数据发布到 GitHub Pages 镜像。没有配置 Cloudflare 部署密钥的管理员也可以只完成审核。

**环境分工**：`main` 是正式环境，只包含真实数据；`dev` 额外带 `data-test/` 测试数据，通过 `npm run deploy:dev` 发布到 `dev.goodcorp.games` 预览。`gdr-survey`、`gdr-admin` 和 `gdr-site` 是三个独立的 Cloudflare Pages 项目，分别对应问卷、审核台和展示站。

## 项目组成

| 模块 | 作用 |
| --- | --- |
| 问卷 | 匿名填写公司、项目、评分、正文和画像 |
| 提交 API | 校验、PoW、限流、去重，写入 D1 |
| 审核控制台 | 本地一键启动，任管理员用 GitHub PAT 登录 |
| 公开数据仓库 | 已审核的公司、项目和评价 JSON |
| 展示站 | Astro 静态站点，按公司和项目聚合展示 |

## 适合谁

- 正在看机会、想提前了解目标公司和项目的游戏从业者
- 想复盘团队真实口碑、但不方便公开表态的在职者
- 需要做行业研究、招聘判断或投资判断的从业者
- 愿意用匿名方式留下真实经历、帮助后来者的离职者

## 免责声明

平台上的内容均为提交者个人观点，平台只做形式审核，不构成对任何公司、项目或个人的事实认定。公司或个人如果认为内容侵犯合法权益，可以通过仓库 issue 或问卷回执号联系管理员，申请删除或更正。

项目目前处于试运行阶段，功能和数据范围会继续调整。

## 管理控制台怎么用

### 启动

1. 安装 Node.js 18+（推荐 22）
2. 双击仓库根目录的 `start-admin.cmd`
3. 浏览器会自动打开 `http://127.0.0.1:8787`；没有自动打开就手动访问

控制台只监听本机，不需要部署，也不把任何密钥写进仓库。

### 登录

控制台用 GitHub PAT 登录。按自己的身份选一种令牌：

#### 仓库主人（管理员）：fine-grained token

1. 打开 https://github.com/settings/tokens?type=beta
2. 点 **Generate new token**
3. Name 填 `gdr-admin`，Expiration 选 30–90 天
4. Resource owner 选 `bkbdq`
5. Repository access 选 **Only select repositories** → `Game-Developer-Review`
6. Permissions → Repository permissions → **Contents** 选 **Read and write**
   （`Metadata` 会自动变成 Read-only，正常）
7. 点 **Generate token**，复制 `github_pat_...`

#### 仓库协作者：classic token

GitHub 的细粒度令牌不支持写别人的个人仓库，协作者请用 classic：

1. 打开 https://github.com/settings/tokens
2. 点 **Generate new token (classic)**
3. Note 填 `gdr-admin`，Expiration 选 30 天
4. Scopes 只勾 **`repo`**
5. 点 **Generate token**，复制 `ghp_...`

两种 token 都只保存在浏览器 cookie（30 天内免登录，点「退出」即清除）；不要写进文件或提交到仓库。登录返回 403 时，先确认 token 对 `bkbdq/Game-Developer-Review` 有 Contents 写权限；仍不行就换另一种令牌。

> 仓库发生过转移或改名后，旧 token（尤其是 fine-grained）会失效，需要按当前 owner `bkbdq` 重新创建；管理员协作者直接改用 classic token 即可。

### 审核

1. 左侧选择一条待审提交
2. 核对公司、项目、正文、标签和在职时长；公司名会优先按提交里的 `companyId` 预选
3. 发布前完成四项检查清单并确认敏感信息提示：正文出现手机号、邮箱、身份证会被标红并禁止发布；疑似微信号 / QQ、住址会黄色提醒；与同公司已发布评价高度相似时会出现提示（可继续发布）
4. 项目可选择「匿名项目」：不公开项目名，公开数据里不关联具体项目
5. 「通过并发布」：写入公开仓 `main`，并把 D1 标记为 `approved`
6. 「拒绝」：选择内部原因（七选一，「其他」需补充说明），标记 D1 为 `rejected`，不写公开仓、不通知提交者

如果同时有多条要处理，可以先点「暂存」：暂存不会写公开仓，也不会触发展示站更新。处理完切到左侧「暂存」标签，点「全部发布」，所有暂存会合并成一次提交、一次展示站更新。暂存只保存在当前浏览器（localStorage），原始提交仍在 D1 待审队列里，不会丢。

新公司/新项目的 ID、slug 会根据名称自动生成（英文名直接转写，中文名追加稳定短哈希），也可以手动修改；名称能匹配到已有公司或项目时会优先复用。

公司 / 项目选择框支持搜索：按名称、ID、别名或旗下项目名模糊匹配并按相似度排序。控制台内置一份常见游戏公司与项目的别名库（`admin/lib/aliases.json`，可随手补充），提交里写「ZZZ」「米哈油」这类写法，打开详情时就会自动匹配到「绝区零」「米哈游」；实在没有匹配时，提交会自动落成新建公司 / 新建项目。

### 给项目和公司配图

双击 `start-artwork.cmd`，或从本机审核控制台进入「配图管理」。目录从 GitHub `main` 读取公司、项目和配图，可按名字搜索，按类型、已配图或缺图筛选。修改已有条目时点「编辑配图」，可以按记录的出处重新读取原图调整裁切，也可以搜索替换图或从本机选图。提交前点「恢复当前配图」可撤回本次编辑。返回目录会保留筛选和本页的编辑进度。

缺图条目可点「配置图片」。项目搜索 Steam、TapTap、腾讯应用宝和百度百科，公司搜索百度百科及维基共享资源。TapTap 优先取同名游戏的商店横幅、封面和图标。有英文名称时还会查英文维基百科。「批量查找缺图」处理当前筛选范围内的缺图条目。需要分批处理时，核对候选后点「暂存到列表」：工具当场按当前裁切生成展示图并暂存到本机浏览器（IndexedDB，不上传）；回到配图管理点「批量上传暂存」，逐条上传 R2 并合并为一次记录提交。

同事更新到最新版，运行 `start-artwork.cmd` 并用原有审核台账号登录，即可点「DeepSeek 找图」。同事电脑无需配置 DeepSeek Key。正式后台在部署时从 GitHub Secret `DEEPSEEK_API_KEY` 同步到 Cloudflare Pages 的生产密钥。已配置本机 Key 的维护机及演练端可继续直接找图。为公司找图时，工具会将公司别名和目录中的代表作品交给 DeepSeek，让它核对开发者身份并指出页面上的具体 Logo。本机工具从检索过的页面核实并下载原图。可提交的图片会出现在候选栏最前面，点选即可预览、裁切和提交。如果没有取得可用原图，工具会尝试常规图片来源并标明出处。成功结果缓存 10 分钟。常规和批量搜索均不会调用 DeepSeek。

百度百科自动取图使用[百度智能云的词条接口](https://cloud.baidu.com/doc/qianfan-api/s/Pmwbl4slf)。在启动工具的本机环境中设置 `BAIDU_BAIKE_API_KEY` 并重新启动，即可按词条名获取主图。也可点「打开百度百科词条」，复制图片或百科图片地址，回到配图页按 Ctrl+V 预览并提交。

核对出处后，点「提交配图」或「保存配图修改」。本机在内存生成 WebP，审核后台将展示图上传到 Cloudflare R2，原图不进存储桶。公司生成主页横幅和目录卡片，项目生成轮播、卡片和详情图。所有图片上传成功后，GitHub `main` 的 `site/public/images/catalog/` 更新 `current.json`，记录版本、出处和裁切参数。批量勾选共用一次记录提交。展示站在此次提交触发的部署完成后显示新版本。

上线时，在 Cloudflare Pages 审核项目 `gdr-admin` 的生产环境绑定 R2 存储桶，变量名为 `ARTWORK`，再部署审核 Functions 和支持 R2 的展示站。上传复用审核台的 GitHub 身份，展示图通过 `https://admin.goodcorp.games/api/artwork/` 按版本读取。下次打开条目会按 `current.json` 记录的出处重新读取原图，供调整裁切；出处失效时按提示重新选图。已有 Git 配图仍可读取仓库原图，演练使用本机独立的 R2 模拟桶。

默认按名称匹配排序。需要 AI 辅助判断归属时，在运行启动脚本前设置环境变量 `GOODCORP_ART_MODEL` 为本机 Ollama 已安装的模型名。工具将搜索词、候选标题和出处传给本机模型，模型判断不确定时留给管理员选图。运行 `npm run test:artwork` 可验证内存裁图、批量提交和仓库回读。

配图上线后可按项核对正式云桶、公开读图和前台展示。[配图管理正式服测试清单](docs/验收/配图管理正式服测试清单.md)

### 更新展示站

- 审核通过后会提交到 `main`，GitHub Actions 的 `site-deploy` 会同时更新 GitHub Pages 镜像 `github.goodcorp.games` 和 Cloudflare 正式站 `goodcorp.games`（`gdr-site`）
- Cloudflare 部署使用仓库加密 Secrets `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID`，不会出现在源码或日志中
- 审核台工具栏的「更新展示站」按钮常驻：本地控制台优先本机部署，失败时自动回退到 GitHub Actions；远程审核台直接触发 Actions，适合没有新数据时重试部署
- 自动部署从 `origin/main` 拉最新数据，不会使用本地未提交的修改
- 开发预览单独发布：在 `dev` 分支执行 `npm run deploy:dev`，构建 `data/` + `data-test/` 并部署到 `gdr-site-dev`（`dev.goodcorp.games`）

### 审计日志

- 通过、拒绝、删除、更正、驳回申请、联系处理、登录成功 / 失败、无权限访问、更新展示站都会写入 D1 `audit_log`
- 审核通过、删除、更正会记录对应的 Git commit SHA，可直接跳转到公开仓的提交
- 审核台右上角「审计日志」可按动作、审核人、日期筛选；日志只存在 D1，不进入公开仓库，也不记录正文、联系方式和 token

可选配置（文件在仓库外）：

```ini
CLOUDFLARE_API_TOKEN=...
CLOUDFLARE_ACCOUNT_ID=...
GIT_PROXY=http://127.0.0.1:7897
```

`GIT_PROXY` 只在拉取 GitHub 需要代理时填写。
