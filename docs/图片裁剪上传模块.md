# 图片裁剪与上传模块设计

> 面向审核控制台（`admin/`）的浏览器端图片处理模块：公司、项目展示图在浏览器内完成裁剪、缩放、压缩，只上传处理后的 WebP，不上传原图。存储使用 Cloudflare R2。

> **实现状态（2026-11-28）**：本文档为早期设计，未按原文实现。实际实现（自 `9ddf8b0` 起）由本机工具裁切：审核台交互为「适配方式 + 水平/垂直焦点」滑杆，真实裁切由 `tools/artwork-library.mjs` 的 sharp 完成；R2 桶绑定在 Pages 项目 `gdr-admin`、变量名 `ARTWORK`，读图走 `https://admin.goodcorp.games/api/artwork/`；尺寸为公司 banner 1440×400、card 720×240，项目 cover 1280×720、card 640×320、detail 1080×480；配图记录写入 `site/public/images/catalog/<公司>/<目标>/current.json`，不写公司 JSON 的 `cover` 字段。本文档的核心原则「原图不上传」已于 2026-11-28 落实：`source` 档不入 R2，编辑配图改为按记录的出处重新读取原图。其余章节仅作设计存档。

## 1. 目标与非目标

### 目标

- 管理员为每家公司和每个项目维护一张展示图，存放在 Cloudflare R2。
- 图片在浏览器端完成裁剪、旋转、缩放、重编码，**原图不离开浏览器、不上传、不落盘**。
- 一次裁剪产出两档尺寸：展示图与缩略图，两者内容一致、比例相同，避免页面二次裁剪失真。
- 上传后把对象 key 写回公司 / 项目数据，走现有「保存修改 → Git 提交 → 构建发布」链路。

### 非目标

- 不做服务端图片处理（不接数据万象、不用 Cloudflare Images 的按量转码）。
- 不做多图相册、不做出图审核流（二期）。
- 不面向公众开放上传，仅管理员在审核台使用。

## 2. 约束与前置条件

| 约束 | 说明 |
| --- | --- |
| 无构建工具 | `admin/` 是原生 ESM，无打包器、无 npm 依赖；模块必须以 `<script type="module">` 直接引入，不得引入第三方裁剪库 |
| CSP | [data.html](../admin/data.html) 的 meta CSP 限定 `img-src 'self' data:`、`connect-src 'self' https://api.github.com`。**预览用 `blob:` 会被拦截，必须加 `blob:`**；同时加图床域名 `https://img.goodcorp.games` |
| 浏览器能力 | 依赖 `createImageBitmap`、`canvas.toBlob`、WebP 编码（Safari 14+ 支持）；编码失败时回退 JPEG |
| 请求体大小 | 单次上传 ≤ 512 KB，兼容 Pages Functions 限制 |
| R2 绑定 | `gdr-admin` Pages 项目绑定 R2 bucket `gdr-images`，变量名 `IMAGES` |
| 公开访问 | bucket 绑定自定义域 `img.goodcorp.games`，只读公开，供展示站读取 |

R2 免费额度（按账号/月）：存储 10 GB·月、Class A 100 万次、Class B 1000 万次、出网流量免费。按 5000 家公司 + 2 万个项目、每实体三档图估算，约 7.5 万个对象、5–6 GB，仍在免费额度内；对象数量本身不产生费用，额度只受 GB·月约束。

## 3. 对象命名与数据契约

### 3.1 对象 key

```
img/companies/{companyId}/cover-1920-{hash8}.webp   # 详情页 / 公司横幅
img/companies/{companyId}/cover-960-{hash8}.webp    # 列表卡 / 公司目录
img/companies/{companyId}/cover-480-{hash8}.webp    # 搜索结果 / 小缩略

img/projects/{projectId}/cover-1920-{hash8}.webp
img/projects/{projectId}/cover-960-{hash8}.webp
img/projects/{projectId}/cover-480-{hash8}.webp
```

- `hash8`：以 1920 档处理后的字节计算 SHA-256 前 8 位十六进制，三档共用同一 hash，便于按组替换和清理。
- 扩展名由实际编码结果决定（`webp` 或回退 `jpg`），三档保持一致，不接受用户文件名。
- 三档 key 由同一 hash 推导（只替换宽度段），数据里**只存 1920 主 key**；校验脚本按同一规则检查，避免出现「主图存在、小档缺失」的引用。

### 3.2 数据字段

| 文件 | 字段 | 规则 |
| --- | --- | --- |
| `data/companies/*.json` | `cover` | 可选，`^img/companies/c_[a-z0-9_-]+/cover-1920-[0-9a-f]{8}\.(webp\|jpg)$` |
| `data/companies/*.json` → `projects[]` | `cover` | 可选，`^img/projects/p_[a-z0-9_-]+/cover-1920-[0-9a-f]{8}\.(webp\|jpg)$` |

- 只存 key，不存完整 URL；域名由构建期 `PUBLIC_IMAGE_BASE` 拼接，换存储商只改一个环境变量。
- `schema/*.schema.json` 需显式新增字段（`additionalProperties: false`），并同步 `scripts/gen-types.mjs` 产物。
- `scripts/validate.mjs` 增加 key 格式校验，禁止 `..`、绝对路径、`http(s)://` 与非法扩展名。

## 4. 输出规格

站点现有容器比例集中在 1.98–2.25 之间，且全部 `object-fit: cover`，因此统一按 **2:1** 出图：

| 档位 | 比例 | 输出尺寸 | 格式 | 硬上限 | 目标实际 | 使用位置 |
| --- | --- | --- | --- | --- | --- | --- |
| `cover` | 2:1 | 1920×960 | WebP q≈0.82 | ≤ 250 KB | 130–180 KB | 首页轮播主图、项目详情主图、公司横幅（均为 LCP 位置） |
| `card` | 2:1 | 960×480 | WebP q≈0.80 | ≤ 90 KB | 45–65 KB | 首页项目卡、公司页项目卡、首页轮播两侧预览 |
| `thumb` | 2:1 | 480×240 | WebP q≈0.78 | ≤ 25 KB | 10–15 KB | 公司目录公司卡与榜单图（取旗下首个项目图）、审核台表单回显 |

各档的落地位置以现有组件为准：首页轮播走 [FeaturedProjects.astro](../site/src/components/FeaturedProjects.astro) 的 `hero-cover`，项目卡走 [ProjectTile.astro](../site/src/components/ProjectTile.astro)，公司目录走 [companies.astro](../site/src/pages/companies.astro) 里 `c.titles[0].thumb`，公司横幅走 [StudioMasthead.astro](../site/src/components/StudioMasthead.astro)。站点搜索下拉（`DiscoverySearch.astro`）目前只展示文字，不涉及图片。

按站点实际渲染宽度换算（容器 1192px：4 列卡约 285px、公司页 2 列卡约 443px、详情主图约 674px、公司横幅约 990px），1920 已覆盖最大 2x 需求，再大没有意义；列表卡用 1920 原图属于纯浪费，必须走 `card` 档。

预算原则：首屏最多一张 `cover`（LCP ≤ 200 KB），其余图片全部懒加载并取 `card`/`thumb`；单页新增图片总量控制在 1 MB 内。250 KB 是 WebP 在 1920×960 下约 1.1 bit/像素的高质量水平，正常 q0.8 压缩多在 130–180 KB，顶到上限说明画面噪点或渐变偏多，应继续降质而不是放宽上限。

补充规则：

- 源图上限：文件 ≤ 10 MB，像素 ≤ 2000 万（如 5472×3648），超出提示先缩小再传，防止解码炸弹。
- 统一铺不透明底色（`#1b2733` 或主题深色），避免透明 PNG 转出来发黑。
- 不保留 EXIF：`createImageBitmap(file, { imageOrientation: 'from-image' })` 先应用方向，再经 canvas 重编码，元数据自然丢弃。
- HEIC 等格式依赖浏览器解码能力；失败时提示「当前浏览器无法读取该格式，请先转为 JPG/PNG」。

## 5. 交互设计

### 5.1 流程

```
选择/拖拽文件 → 编辑器弹层 → 裁剪(移动+缩放) → 可旋转 90° 步进
→ 实时预览三档效果 → 确认 → 生成三档 → 上传 → 返回 key → 填入表单草稿
```

### 5.2 编辑器要求

- 裁剪框比例固定为 2:1，**不允许自由拉伸**，只能移动与缩放；缩放范围 1×–4×，不得裁出源图边界。
- 画布内显示三分线辅助构图；画布外区域压暗。
- 操作方式：
  - 鼠标/触屏单指拖动移动画面，滚轮/双指捏合缩放；
  - 键盘：方向键 1px、`Shift`+方向 10px、`+/-` 缩放、`Enter` 确认、`Esc` 取消；
  - 旋转按钮按 90° 步进（0/90/180/270），不做任意角度旋转。
- 右侧或底部固定展示三档预览（1920 / 960 / 480 宽的等比缩略），标注各自预估文件大小；某一档超出硬上限时对应预览标红提示。
- 按钮：`取消` / `恢复`（重置到初始构图） / `确认并上传`；点击区域 ≥ 44px。
- 弹层：`role="dialog"`、`aria-modal="true"`、焦点锁定、关闭后焦点回到触发按钮。

### 5.3 状态机

`idle → loading(解码) → editing → encoding → uploading → done | error`

- `error` 保留用户已做的裁剪状态，提供「重试」。
- `uploading` 显示百分比进度与取消入口（取消即中止 fetch，不产生半截对象）。
- 已存在 `cover` 时按钮文案为「替换封面」，并展示当前封面缩略图。

### 5.4 隐私

- 原图仅以内存 `File` + `URL.createObjectURL` 存在，模块结束或取消时立即 `revokeObjectURL` 并置空引用。
- 不把原图或处理后二进制写入 `localStorage`；草稿区只存 key 与尺寸等元数据。

## 6. 模块拆分

```
admin/lib/image-geometry.js   # 纯函数：源矩形计算、边界夹紧、key/hash 生成、扩展名回退

admin/lib/image-uploader.js   # 上传：fetch、进度、超时、指数退避重试
admin/lib/image-editor.js     # UI：弹层、拖拽/缩放手势、状态机、无障碍
admin/image-editor.css        # 编辑器样式（复用现有 .panel/.actions 视觉）
scripts/test-admin-image.mjs  # Node 侧纯函数测试，挂 npm run test:admin-image
```

`image-geometry.js` 不依赖 DOM，才能在 Node 下直接测试，符合仓库现有 `scripts/test-admin-*.mjs` 的测试约定。

## 7. 编码策略

1. 解码：`createImageBitmap(file, { imageOrientation: 'from-image' })`。
2. 裁剪：状态为 `{ zoom, offsetX, offsetY, rotation }`，由它推导源矩形 `{ sx, sy, sw, sh }`（比例固定 2:1），并夹紧在源图范围内。
3. 绘制：`ctx.drawImage(bitmap, sx, sy, sw, sh, 0, 0, outW, outH)`，直接按目标尺寸绘制，**不做二次缩放**。
4. 分档编码：三档共用同一次裁剪结果，各自独立绘制、独立编码，保证构图一致；初始质量与硬上限如下。

| 档位 | 输出尺寸 | 初始 q | 硬上限 | 目标实际 |
| --- | --- | --- | --- | --- |
| cover | 1920×960 | 0.82 | 250 KB | 130–180 KB |
| card | 960×480 | 0.80 | 90 KB | 45–65 KB |
| thumb | 480×240 | 0.78 | 25 KB | 10–15 KB |

5. 降质循环：单档超出硬上限时 `q -= 0.04` 重新编码，最低 0.62；仍超出则尺寸按 0.9 缩小，最多 3 轮；任一轮达标即停止，三档互不影响。
6. 不二次缩放：每档直接按目标尺寸 `drawImage`。源图裁剪后有效宽度小于该档时不拦截、按档输出（页面侧有 CSS 尺寸约束，略软可接受），以保证三档 key 恒定存在、`srcset` 可安全引用。
7. 回退：`toBlob` 返回 `null` 或浏览器不支持 WebP 编码时，改用 `image/jpeg`，三档 key 扩展名同时变为 `jpg`。
8. 并发：三档并行编码、串行上传；同时只允许一个编辑会话。

## 8. 上传协议

`POST /api/admin/upload`（Pages Function，位于 `admin/functions/api/admin/upload.js`）

- 鉴权：复用 `admin/functions/api/admin/_middleware.js` 现有登录校验，未登录返回 401；校验 `Origin` 为审核台域名。
- 请求：`Content-Type: image/webp|image/jpeg`，`X-Object-Key: img/...`，body 为二进制。
- 服务端校验：
  - key 正则白名单（见 3.1），拒绝 `/` 逃逸与非法字符；
  - 长度 ≤ 512 KB；
  - magic bytes 校验（`RIFF....WEBP` / `FFD8FF`），拒绝 SVG/HTML；
  - 缺失或非法返回 400 / 415 / 413。
- 写入：

```js
await env.IMAGES.put(key, request.body, {
  httpMetadata: {
    contentType: request.headers.get('content-type'),
    cacheControl: 'public, max-age=31536000, immutable',
  },
});
```

- 幂等：先 `env.IMAGES.head(key)`，已存在直接返回成功，省一次写操作。
- 响应：`{ ok: true, key, size }`。

## 9. 与数据写入的关系

- 上传成功只代表对象就位，数据变更仍走现有「保存修改」→ GitHub commit → Actions 构建 → 发布。
- 顺序固定：**先传图，后存 JSON**。JSON 保存失败最多留下孤儿对象，不会产生坏引用。
- 替换封面会生成新 hash，旧 hash 的三档对象成为孤儿；删除时按旧 hash 前缀一次性移除三档。清理列为后续可选任务：按仓库内所有 `cover` 引用做白名单，列出未被引用的对象后人工确认删除（不阻塞一期上线）。
- 上线前给展示站加一条兜底：`cover` 缺失或加载失败时回退 `images/studio.webp`，避免破图。

## 10. 展示站改动

- `site/src/lib/data.ts` 增加 `img(key)`：`key` 为空返回 `null`，否则拼 `PUBLIC_IMAGE_BASE`。
- `site/src/lib/projects.ts` 删除 `artwork` 硬编码表，改读数据里的 `cover`。
- `StudioMasthead.astro` 去掉 `cloudcape` 特判，优先用 `company.cover`。
- `<img>` 补 `width`/`height` 或外层 `aspect-ratio`，图片懒加载；`srcset` 用 480/960/1920 三档并配 `sizes`：卡片只取 480 或 960，详情主图与公司横幅取 1920，首屏仅一张 1920 图预加载。
- `site/public/_headers` 的 `img-src` 增加 `https://img.goodcorp.games`；构建注入 `PUBLIC_IMAGE_BASE=https://img.goodcorp.games`。
- 审核台 meta CSP 增加 `blob:` 与图床域名，否则预览和回显都会被拦。

### 手工清单

| 场景 | 预期 |
| --- | --- |
| 6000×4000 大图 | 正常解码，三档均不超硬上限（≤ 250 / 90 / 25 KB） |
